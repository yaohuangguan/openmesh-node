02 · Code

Start small.
Add the mesh when you need it.

HTTP routing is useful by itself. Database lifecycle, discovery, traffic policy, workload identity and peer calls are separate layers rather than mandatory ceremony.

server.ts 
import openmesh from 'openmesh-node';
import { bodyParser } from 'openmesh-node/plugins';

const app = openmesh();
app.use(bodyParser());

app.get('/users/:id', ({ params }) => ({
  id: params.id
}));

await app.listen({ port: 3000 });

04 · Why OpenMesh

The difference is not another router.

OpenMesh keeps the HTTP core small, then adds the service-runtime concerns that usually become separate libraries, sidecars and application glue.

01

Start as an API. Grow into a mesh.

Keep normal app.get/post routes, your existing ORM and application lifecycle. Add lazy app.mesh('service') handles only when services split.

02

Discovery and traffic policy are live runtime state.

Registration leases, resumable membership watches, weighted subsets, header routes, locality preference and live policy replacement feed the same warm service pool.

03

Failure and overload stay bounded.

Deadlines, safe retries, circuits, queues, bulkheads, adaptive concurrency and true streaming semantics are part of peer calls rather than scattered caller code.

04

Identity and telemetry stay inside the application boundary.

SPIFFE-style workload identity, mutual TLS, certificate rotation, trace propagation and an OpenTelemetry-compatible metrics bridge remain opt-in runtime layers.
